# نظام زوار مستشفى الزرقاء الحكومي (HVMS)

**التشغيل الأمني:** الصخرة للخدمات والاستشارات الأمنية — Rock

تطبيق Android مبني باستخدام **Flutter وDart**، بواجهة عربية من اليمين إلى اليسار، لتنظيم تسجيل الزوار وحركة الدخول والخروج ومتابعة المناوبات والتقارير بين ضابط الأمن والمشرف والمسؤول الإداري.

- **المستودع:** https://github.com/maloohm-collab/hospital-visitor-system
- **الفرع الرئيسي المعتمد:** `main`
- **آخر إصدار أساسي معتمد:** دمج PR #2 — `bec8dc83c5cde37c2340df188c5c64895f6fe383`
- **حالة المشروع:** النسخة الحالية معتمدة للاستخدام التجريبي وفق اختبار المستخدم على الجهاز. أي تطوير لاحق ينفذ كتحديث منفصل.
- **البناء:** GitHub Actions يدوي فقط؛ لا يفترض أن يبدأ بناء APK تلقائيًا مع كل تعديل.

## الدليل الكامل للمشروع

راجع **[PROJECT_DOCUMENTATION.md](PROJECT_DOCUMENTATION.md)** للحصول على دليل المشروع من الألف إلى الياء: وصف النظام، الأدوار والصلاحيات، سير العمل، الطوابق والأقسام، مجموعات Firestore، إعداد Firebase، قواعد الأمان، التقارير، البناء، الاختبار، التشغيل والصيانة واستكشاف الأخطاء.

## الوظائف الأساسية

- تسجيل الدخول بالبريد الإلكتروني وكلمة المرور عبر Firebase Authentication.
- طلبات إنشاء حساب لضابط الأمن أو المشرف، مع انتظار اعتماد المسؤول.
- إدارة حسابات الموظفين وحالاتهم وأدوارهم من الحساب الإداري وفق الصلاحيات.
- تسجيل زيارات متعددة وغير محدودة عمليًا ضمن المناوبة، مع الطابق والقسم والغرفة وعدد الزوار ووقت الدخول والخروج والملاحظات.
- البحث في سجلات الزيارات، ومتابعة الزيارات التي لم يكتمل خروجها.
- لوحات ملخص وإحصاءات للزيارات حسب التاريخ والطابق والقسم والحالة.
- إنشاء تقارير PDF باللغة العربية ومشاركتها بحسب إمكانات الجهاز.
- شاشات منفصلة حسب الدور لضابط الأمن والمشرف والمسؤول الإداري.
- تقارير المناوبة والحوادث والملاحظات والتوصيات ومسار رفع التقارير الإدارية وفق سير العمل الموجود في التطبيق.
- سجل الزيارة المشترك محفوظ في Firestore؛ إخفاء السجل من قائمة المستخدم لا يعني بالضرورة حذف السجل المشترك.
- واجهة عربية RTL، مع تهيئة الخطوط والنصوص العربية في ملفات PDF.

## الأدوار

| الدور | المسؤوليات العامة |
|---|---|
| ضابط الأمن — `security_officer` | تسجيل الزيارات، تسجيل الخروج والملاحظات، مراجعة السجلات المسموح بها، وإعداد التقارير وإرسالها ضمن الصلاحيات. |
| المشرف — `supervisor` | مراجعة سجلات وتقارير الموظفين، إعداد الملاحظات والتوصيات والتقارير، ورفع ما يلزم للإدارة حسب سير العمل. |
| المسؤول الإداري — `admin` | إدارة حسابات الموظفين وطلبات التسجيل والحالات، ومراجعة السجلات والتقارير والإشراف على النظام. |

قواعد Firestore هي طبقة التفويض الأساسية للبيانات؛ إخفاء زر في الواجهة وحده لا يعد حماية كافية.

## الطوابق والأقسام

- **الطابق الخامس:** العناية الحثيثة والحروق.
- **الطابق الرابع:** الجراحات التخصصية — عظام الرجال، عظام النساء، وقسم الأطفال.
- **الطابق الثالث:** الباطنية — رجال ونساء.
- **الطابق الثاني:** الجراحة — رجال ونساء.
- **الطابق الأول:** التوليد والولادة وحديثو الولادة.
- **CCU — منطقة مستقلة:** العناية القلبية الحثيثة وخدمات القلب والقسطرة.

## التقنية والبيانات

- Flutter / Dart لتطبيق Android.
- Firebase Authentication للمصادقة.
- Cloud Firestore لملفات المستخدمين وطلبات الحسابات وسجلات الزيارات وبيانات التقارير التي يحددها التطبيق وقواعد البيانات المنشورة.
- `pdf` و`printing` و`share_plus` لإنشاء التقارير وعرضها أو مشاركتها.
- `intl` للتنسيق الزمني، و`arabic_reshaper` لتشكيل النص العربي في سياق PDF.
- ملف القواعد المرجعي داخل المستودع هو [firestore.rules](firestore.rules).

**تنبيه:** وجود ملف القواعد في GitHub لا ينشره تلقائيًا إلى Firebase. يجب نشر القواعد من Firebase Console، وقد أكد مالك المشروع أن النشر تم للنسخة الحالية.

## إعداد البيئة لأول مرة

1. ثبّت Flutter المتوافق مع قيود SDK في `pubspec.yaml` وAndroid SDK وJava 17.
2. اربط التطبيق بمشروع Firebase الصحيح.
3. أضف ملف إعداد Android الصحيح إلى `android/app/google-services.json`؛ لا ترفع مفاتيح خاصة أو بيانات سرية إلى المستودع.
4. فعّل Email/Password في Firebase Authentication.
5. أنشئ حساب المسؤول في Authentication، ثم أنشئ ملفه الإداري الموثوق في `users/{UID}` وفق بنية القواعد المنشورة. يجب أن يحتوي الدور والحالة والبيانات المطلوبة وفق الكود والقواعد.
6. راجع ملف `firestore.rules` وانشره من Firebase Console > Firestore Database > Rules > Publish.
7. من جذر المشروع شغّل:

   ```bash
   flutter pub get
   flutter test
   ```

8. لا تعتبر نجاح البناء وحده دليلًا على إعداد Firebase أو صلاحيات الحسابات؛ يجب أن يكون المشروع مربوطًا بالمشروع الصحيح وأن تكون القواعد منشورة.

## بناء APK

البناء الآلي مضبوط ليُشغّل **يدويًا** من GitHub Actions:

1. افتح [Build APK workflow](https://github.com/maloohm-collab/hospital-visitor-system/actions/workflows/build-apk.yml).
2. اضغط **Run workflow** واختر الفرع المطلوب، ويفضّل `main` للإصدار المعتمد.
3. انتظر انتهاء المهمة وتحقق من حالة جميع خطواتها.
4. عند نجاحها، افتح تشغيل الـ workflow ونزّل artifact باسم `hospital-visitor-system-apk` إذا كان الاسم ظاهرًا بهذا الشكل في ذلك التشغيل.
5. ثبّت APK على جهاز الاختبار وتحقق من تسجيل الدخول والأدوار واتصال Firebase قبل التوزيع.

لا يتم البناء تلقائيًا بعد كل تعديل وفق الإعداد الحالي. وقد تختلف أسماء artifacts أو تفاصيل الخطوات إذا تم تحديث workflow لاحقًا.

## الاختبارات والتحقق قبل أي إصدار

- تسجيل الدخول والخروج لكل دور.
- طلب حساب جديد، ومراجعة الطلب واعتماده أو رفضه.
- التأكد من منع الحساب المعلّق أو المحظور من الدخول وفق حالة الحساب.
- إنشاء زيارة، ثم إكمال الخروج وإضافة الملاحظات.
- تسجيل أكثر من زيارة والتحقق من عدم تكرار السجل لنفس الزيارة.
- مراجعة السجلات والصلاحيات لكل دور.
- اختبار تقارير PDF: اتجاه العربية، الأسماء، الهاتف، التاريخ، الأوقات، الأعداد، والمشاركة.
- اختبار تقارير المناوبة والإشراف ورفع التقرير إلى الإدارة.
- التأكد من رفض Firestore لأي عملية غير مسموحة بالقواعد.
- التحقق من أن التقرير لا يضم بيانات لا يملك المستخدم صلاحية الوصول إليها.

## الخصوصية والأمان

- لا تحفظ كلمات المرور أو بيانات الاعتماد السرية داخل ملفات المصدر.
- لا تجعل حساب المسؤول متاحًا بالتسجيل الذاتي؛ يجب إعداد صلاحياته بشكل موثوق.
- لا تعتمد على صلاحيات الواجهة فقط؛ تحقق من قواعد Firestore.
- لا تحذف سجلات مشتركة أو تاريخًا مطلوبًا للتدقيق لمجرد إخفائها من قائمة المستخدم.
- بيانات الزوار وسجلات المستشفى بيانات حساسة؛ يجب تقييد الوصول إليها وحماية أجهزة الاستخدام والنسخ الاحتياطية.
- يجب على مالك النظام مراجعة سياسات الاحتفاظ بالبيانات والصلاحيات ومتطلبات المؤسسة قبل الاستخدام التشغيلي الرسمي.
